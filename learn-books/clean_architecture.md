# Clean Architecture

## アーキテクチャは技術依存ではない

これが最重要。

Uncle Bob は、

- Web
- DB
- GUI
- 並列処理
- 組み込み
- AI
- Framework

みたいな“技術差分”よりも、

「ソフトウェアをどう分割するか」

の方が本質だと言っている。

つまり Clean Architecture は、React や Next.js の話ではなく、

「変更に耐える構造」

の話。


## 「本質的な計算モデルは変わっていない」

- if
- while
- assignment

など、本質的には変わってないと言っている。

つまり、「技術進化 ≠ 本質進化」ということ。


## アーキテクチャとは複雑性制御

ハードウェア性能は10²²倍進化した。

なのにソフトウェア開発は今も苦しい。

なぜか。

計算能力ではなく、“複雑性” が問題だから。

だから Clean Architecture は、

「どう複雑性を制御するか」

の理論。



## 過去のルールは今でも通用する
新技術ばかり追うと、

- Framework依存
- 流行依存
- ツール依存

になりやすい。

でも Uncle Bob は、「変わらない原理を学べ」と言っている。

これはコンピュータサイエンス的視点。


## 「動くコード」と「良いコード」は別物

ここが核心。

Uncle Bob は最初に、

「動かすだけなら難しくない」

と言い切っている。

つまり彼は、プログラミングの本質を実装能力ではなく構造設計能力に置いている。

これはかなり重要。


## ソフトウェア開発の本当のコストは変更

この章全体で彼が言いたいのは、「最初に動くこと」ではなく、「変更し続けられること」が本質だということ。

悪い設計だと、

- 小変更が巨大コスト化
- バグ連鎖
- 開発速度低下
- 人海戦術化

が起きる。

これは現代開発そのもの。


## 「良い設計は人数依存を減らす」

かなり本質的。

普通は、

「大規模開発＝大量人員」

と思われがち。

でも Uncle Bob は逆を言っている。

良い設計なら、

- 少人数
- 小コスト
- 高変更性
- 低バグ率

で回る。

アーキテクチャは“人間の負荷”を減らす技術。



## 「悪い設計は組織を壊す」

これは実務経験ある人ほど刺さる。

悪い設計は単に技術問題じゃない。

- チーム崩壊
- 信頼低下
- マネジメント疲弊
- 開発文化悪化

まで波及する。

つまりソフトウェア設計は、組織設計でもある。


## プログラミングは職人技

ここも重要。

彼は単なる知識ではなく、

- discipline（規律）
- dedication（献身）
- craft（職人性）

を強調している。

つまり Clean Architecture は、単なる設計パターン集ではなく、

「プロとしてどう作るか」

の思想書でもある。


## 「アーキテクチャ = 高レベル設計」ではない

ここかなり重要。

普通は、

- Architecture = 上流
- Design = 実装

みたいに分ける。

でも Uncle Bob は、

「それは幻想」

と言ってる。

設計は連続体。

つまり、

- クラス分割
- 関数責務
- モジュール依存
- DB分離
- レイヤー構造

全部がアーキテクチャ。

これはかなり本質的。



## 「設計品質 = 将来コスト」

ここが Clean Architecture の中心思想。

彼は美しさで測ってない。

「変更コスト」

で測ってる。

つまり良い設計とは、

- 変更容易
- 理解容易
- 保守容易
- 拡張容易

な設計。

逆に悪い設計は、未来に負債を積み続ける。



## 「人を増やしても解決しない」

超重要。

壊れた設計に人を追加すると、むしろコストが加速する。

これは現実でもかなり起きる。

理由は、問題が「実装量」ではなく、「複雑性」だから。

つまり設計崩壊すると、

- 認知負荷
- 依存関係
- 修正影響範囲

が爆発する。

だから人数では解決できない。


## 「開発者の仕事が“価値創造”から“混乱管理”に変わる」

この表現はかなり鋭い。

本来開発とは、「新しい価値を作ること」のはず。

でも設計崩壊すると、

- 壊さないための調整
- 副作用対応
- バグ回避
- 依存修復

ばかりになる。

つまり、“複雑性維持装置”になってしまう。


## 「Clean Architecture の本質」

この章までで、本のテーマがかなり見えてくる。

結局この本は、

「どう書くか」

ではなく、

「どう壊れない構造を作るか」

の本。

さらに言えば、

「人間が継続的に理解可能な状態をどう維持するか」

の本でもある。


## 「後で綺麗にする」は幻想

これは Clean Code / Clean Architecture 系で最重要思想の一つ。

Uncle Bob はかなり強く、

「あとで直す時間は来ない」

と言っている。

実際の現場でもかなりそう。

- 次機能
- 緊急対応
- バグ修正
- 納期
- 市場競争

が永遠に続く。

だから最初から整えて進む必要がある。


## 「汚いコードの方が短期的にも遅い」

ここ超重要。

普通は、

- 綺麗 = 遅い
- 雑 = 速い

と思われがち。

でも彼は逆を言っている。

これはかなり深い。

なぜなら、
コードを書く速度ではなく、

“理解速度”

が開発速度を決めるから。

汚いコードは、

- 読解コスト
- 副作用調査
- 修正影響確認
- バグ探索

を増やす。

つまり、
書く瞬間から既に遅い。


## 「Clean Architecture は認知負荷管理」

この章でかなり見えてくる。

本当の敵は、

- CPU不足
- 言語不足
- フレームワーク不足

じゃない。

敵は、

“人間の理解限界”

。

だから Clean Architecture の本質は、

「人間が理解可能な状態を維持する構造」

なんです。


## 「作り直し神話」を否定している

これも重要。

現場ではよく、

「もう全部作り直そう」

となる。

でも Uncle Bob は、

「同じ思考のままなら再崩壊する」

と言っている。

つまり問題はコードではなく、
思考様式。

かなり本質的。


## 「The only way to go fast, is to go well」

この本の中心思想の一つ。

かなり有名な一文。

つまり、

- 品質
- 整理
- 責務分離
- テスト
- 設計

はコストではなく、
“速度向上手段”。

ここが現代開発で最も誤解されやすい部分。


1. 「ソフトウェアの本質は“変更容易性”」

これは Clean Architecture の超中心思想。

かなり重要。

ソフトウェアは、

“動くこと”

“変えられること”

が本質。

だから software は soft。

ここめちゃくちゃ深い。


2. 「変更コストは構造で決まる」

同じ規模変更でも、

- 良い構造
    → 小コスト
- 悪い構造
    → 巨大コスト

になる。

つまり開発速度は、
人間性能ではなく、
構造性能。


3. 「機能優先」は長期的に機能を壊す

短期的には機能優先が正しそうに見える。

でも構造無視すると、
最終的に変更不能になり、
機能追加速度が崩壊する。

これはかなり現代的問題。


4. 「アーキテクチャは“未来の自由”」

かなり本質的。

良い設計とは、
未来変更の自由度を維持すること。

つまりアーキテクチャは、

“未来の選択肢を守る技術”

。


5. 「開発者はコードを書く人ではない」

ここ重要。

Uncle Bob の世界観では、開発者の本当の責任は、「長期的に変更可能な構造を守ること」。

単なる実装者ではなく、“複雑性管理者”


. 「パラダイム = 制約」

ここ超重要。

普通、
技術進化って、

“自由が増える”

と思われる。

でも Uncle Bob は逆を言う。

本当に重要な進化は、

“状態変更制御”

変更可能状態は、
複雑性源だから。


5. 「アーキテクチャ = 複雑性制御技術」

この章でかなり明確になる。

結局アーキテクチャとは、

- 制御フロー
- 依存関係
- 状態変更

を制御することで、“人間が扱える複雑性に抑える”技術。


1. 「構造化プログラミングの本質は readability ではない」

ここ超重要。

一般には、「goto を減らして読みやすくする」くらいに理解される。

本質は、“証明可能性”。

つまり、“人間が正しさを追える構造”にすること。

ダイクストラの出発点はここ。

人間の脳は、巨大複雑性を保持できない。

だから必要なのは、

“複雑性分割”

これは Clean Architecture 全体の中心思想。


3. 「構造化 = 分割統治可能性」

if / while の重要性は、

つまり、

- 小さく分けられる
- 局所理解できる

これがアーキテクチャの基礎になる。


4. 「ソフトウェア工学は数学を目指していた」

かなり重要。

昔の研究者たちは、ソフトウェアを単なる職人技ではなく、“証明可能な科学”にしたかった。

現在の、

全部この流れの延長。


5. 「Clean Architecture の本質は“人間認知支援”」

これがかなり大事。

結局、構造化プログラミングも、“人間が理解可能な単位へ分解する”ための技術。

つまりアーキテクチャとは、“認知限界との戦い”


1. 「構造化の本質は testability」

かなり重要。

読みやすさだけじゃない。

これめちゃくちゃ重要。

モジュール。

4. 「制約は検証可能性を生む」

goto禁止も、結局はここ。

自由を減らすことで、

- 理解可能
- 分解可能
- テスト可能

になる。



5. 「アーキテクチャは科学実験可能性の設計」

かなり深い。

Clean Architecture の本質は、“変更やテストによって、システムの正しさを観測可能にすること”とも言える。

アーキテクチャ = 検証容易性設計。

かなり重要。

- 継承

つまり Clean Architecture における OOP は、“変更方向を制御するための技術”

。

ここかなり深い。

でも Uncle Bob は、

4. 「本当に重要なのは依存方向」

この流れ、次章のポリモーフィズムへ繋がる。

Clean Architecture において、OO の本当の革命は、

“依存関係逆転”

だから。

継承自体は、そこまで重要視されていない。


5. 「抽象化とは“同じものとして扱える”こと」

NamedPoint を Point として扱える。

これが抽象化の根本。

つまり抽象化とは、“異なる実体を、共通インターフェースとして扱うこと”。


もう少し整理すると、Uncle Bob 的な OO の本質は、「具体的な違いを隠し、共通の約束(interface)として扱えるようにすること」。

例えば copy プログラム。

copy 側から見ると、

- キーボード
- ファイル
- ネットワーク
- 音声入力

の違いは存在しない。

全部、

write()

できる “何か” として扱われる。

つまり、“違いを消して、同じものとして扱える”。

これによって初めて、

- 差し替え
- 拡張
- 独立開発
- plugin化

が可能になる。


オブジェクト指向とは、「異なる実装を、共通の振る舞いとして扱うための規律」

とか、「変更される具体と、変更したくない抽象を分離する技術」とも言える。

Clean Architecture 文脈ではさらに、

「依存方向を制御するための仕組み」

という意味がかなり強い。

つまり interface は、単なる “共通化” ではなく、“高レベル側を低レベル変更から守る壁”

だから Uncle Bob は、

- class
- inheritance
- encapsulation

より、polymorphism を圧倒的に重視してる。


これが最大核心。

Uncle Bob にとって OO は：

“依存方向制御技術”

。


2. 「実行方向と依存方向は別」

超重要。

interface は抽象化ではなく、

“依存方向を曲げる壁”

。

かなり重要。

Clean Architecture の目的は：

高レベル policy
（ビジネスルール）

を、

低レベル detail
（DB/UI/framework）

から守ること。


5. 「低レベルは plugin」

ここめちゃ重要。

DB は中心じゃない。

Framework も中心じゃない。

全部 plugin。

つまり交換可能。


自分の言葉で言うなら

「OO とは、違いを吸収して同一視することで、依存方向を自由に制御する技術」

さらに Clean Architecture 的に言うと、

「変わりやすい具体を、interface の外側へ追放し、変えたくない本質を守る技術」

になる。


1. 「mutable state が複雑性の源」

超重要。

OO の章では：

依存方向が複雑性源だった。

ここでは：

mutable state が複雑性源。


2. 「関数型の本質は immutability」

map/filter が本質じゃない。

本質は：state changes を減らす


3. 「アーキテクチャは“変更隔離”」

これ面白い。

Clean Architecture 全体通して、

- dependency change
- technology change
- state change

全部隔離しようとしてる。


4. 「Concurrency 問題 = state sharing 問題」

かなり本質。

thread が危険なんじゃない。

共有 mutable state が危険。


5. 「純粋関数は testability を上げる」

前章の falsifiability にも繋がる。

pure function は：

- 入力固定
- 出力固定
- 副作用無し

だから超テストしやすい。


OO と Functional の役割分担

ここかなり重要。

Uncle Bob は最後で言ってた。


OOP

→ dependency management

（依存方向制御）


Functional

→ data/state management

（状態管理）

Structured Programming

→ algorithm decomposition

（分解と検証）


ここでようやく、Clean Architecture の中心的な土台である SOLID に入った。

この章で重要なのは、

「SOLID はテクニック集ではない」

ということ。

著者はかなり明確に、良いアーキテクチャは、良いコードから始まると言っている。

つまり architecture は、巨大な設計図だけの話ではなく、日々書くクラスや関数の積み重ね。

だから SOLID は、“コードレベルの作法” でありながら、
実際には architecture を成立させるための中間層になっている。

ここで言ってる “mid-level structure” はかなり重要。



構造をレベル分けすると、

- Low-level → 関数・変数・アルゴリズム
- Mid-level → クラス・モジュール・依存関係（SOLID）
- High-level → コンポーネント・システム構造（Architecture）

になる。

つまり SOLID は、「小さいコード」と「大きいアーキテクチャ」を繋ぐ橋。



あと、ここでの定義がかなり本質的。

SOLID の目的は：

- 変更に耐える
- 理解しやすい
- 再利用可能

な構造を作ること。

結局また、“変化への耐性”に戻ってくる。

この本は本当に一貫している。

それぞれを本質だけでまとめるとかなり面白い。


SRP（単一責任原則）

「変更理由を1つにする」

普通は「1クラス1役割」みたいに説明される。

でも Uncle Bob は、“誰の要求で変わるか”を重視してる。

つまり責任とは、機能ではなく「変更圧力」。

これはかなり重要。


OCP（開放閉鎖原則）

「追加には開き、変更には閉じる」

つまり、既存コードを壊さず、拡張で振る舞いを変える。

ここで polymorphism と interface が効いてくる。

実際、Clean Architecture 全体がOCP を巨大化した思想とも言える。


LSP（リスコフの置換原則）

これはかなり誤解されやすい。

本質は、「差し替えても世界が壊れない契約」

継承の話ではなく、“期待される振る舞い” の話。

つまり interface の信頼性。

ここが崩れると plugin architecture が壊れる。


ISP（インターフェース分離原則）

「使わないものに依存するな」

これは認知負荷の削減でもある。

巨大 interface は、
不要な変更伝播を生む。

だから interface は、
利用者単位で細かく分ける。


DIP（依存性逆転原則）

これはこの本の中核。

「詳細ではなく方針に依存させる」

DB
UI
Framework
API

みたいな“変わりやすい詳細”ではなく、

Business Rule
Use Case

みたいな“本質”を中心に置く。

つまり dependency inversion は、「構造の重心を本質側に置く」ための原則。


かなり面白いのは、

SOLID 全体を見ると、全部同じ方向を向いていること。

全部、

- 変更の局所化
- 認知負荷削減
- 依存制御
- 本質と詳細の分離

をやってる。

つまり SOLID は、単なる5原則ではなく、「複雑化に対抗するための構造原理」。

かなり“設計哲学”に近い。


SRP（単一責任原則）の本質は、

「1つのモジュールが、複数の変更理由を持たないようにする」

こと。

ここで重要なのは、「1つのことをする」ではなく、「誰の要求で変更されるか」という視点。

つまり責任とは、機能単位ではなく、“変更圧力” の単位。


例えば、

- 経理が変更したいコード
- 人事が変更したいコード
- DBA が変更したいコード

が同じクラスに入っていると、一方の変更が他方を壊す。

すると、

- 意図しないバグ
- マージ衝突
- 変更コスト増大
- 認知負荷増加

が起きる。

つまり SRP は、「変更の影響範囲を局所化する原則」とも言える。


Clean Architecture 的には、SRP は単なるクラス設計ではなく、「変更軸ごとに境界を作る」思想。

つまり、異なる理由で変わるものを分離し、同じ理由で変わるものをまとめる。

これによって、

- 理解しやすく
- 安全に変更でき
- チーム間干渉を減らせる

構造になる。

かなり本質的には、「複雑性を、人間が扱える単位へ分解する原則」と言える。



OCP（Open-Closed Principle：開放閉鎖原則）は、

「ソフトウェアは“拡張”には開かれていて、“修正”には閉じているべき」

という考え方です。

つまり、新しい機能を追加するときに、既存コードを大量に書き換えるのではなく、
“追加”によって対応できる設計にしておく、ということです。

たとえば、

- Web画面表示しかなかったシステムに
- PDF出力や印刷機能を追加したい

となったときに、

既存の業務ロジックを壊しながら修正するのではなく、

- 業務ロジック
- 表示用処理
- 印刷用処理

を分離しておけば、印刷機能を「追加」するだけで済みます。

この原則の本質は、「変わりやすいもの」と「変わってほしくないもの」を分離し、重要なルールを変更から守る

という点にあります。

特にアーキテクチャでは、

- UIは変わりやすい
- DBも変わりやすい
- 外部APIも変わりやすい

一方で、

- ビジネスルール
- ドメイン知識
- 中核ロジック

は守りたい対象です。

なので依存関係を、

UI → ビジネスルール ← DB

のように組み、中心のビジネスルールが外側の変更に影響されないようにします。

つまりOCPは、

「変更を局所化し、システム全体への影響を最小化するための原則」

と言える。

この部分は、OCPを実現するために重要なのが「依存関係の向きの制御」だと言っています。

普通に実装すると、

- ビジネスロジック（Interactor）
    → DB
    → UI

に依存しがちです。

でもそれだと、

- DB変更
- UI変更
- フレームワーク変更

がビジネスロジックへ波及してしまいます。

そこでインターフェースを挟みます。

たとえば、

- Interactor は FinancialDataGateway という抽象だけを見る
- 実際のDB実装はそのインターフェースを実装する

こうすると依存方向が逆転します。

つまり、

「高レベルなルールが低レベル実装を知らない」

状態になります。

これが Dependency Inversion（依存関係逆転）の本質です。

さらに FinancialReportRequester のようなインターフェースは、
単に依存方向を変えるだけではなく、

「内部詳細を隠す」

ためにも存在しています。

これは Information Hiding（情報隠蔽）です。

Controller は、

- Entity の内部構造
- Interactor の詳細

を知らなくていい。

必要最小限の窓口だけを知ればいい。

なぜこれが重要かというと、内部知識を持つほど“変更の影響範囲”が広がるから。

つまりOCPの核心は、

- 変更されやすいものを分離し
- 依存方向を制御し
- 内部詳細を隠し
- 中核ロジックを守る

ことにあります。

結果として、「新機能追加 = 既存コード破壊」になりにくい構造を作れます。



LSP（リスコフの置換原則）は、

「ある型を使っている場所に、その派生型を入れても、利用側の振る舞いが壊れてはいけない」

という原則です。

もっと簡単に言うと、

「親として扱えるなら、子に差し替えても同じように使えるべき」

ということです。

たとえば License を親として、

- PersonalLicense
- BusinessLicense

が存在していても、

利用側（Billing）は

license.calcFee()

を呼ぶだけでよく、
内部計算方法の違いを意識しません。

これは「置換可能」なのでLSPを満たしています。

一方、有名な違反例が
「Square と Rectangle」です。

直感的には、

- Square は Rectangle の一種

に見えます。

でも Rectangle は、

- width と height を別々に変更できる

という前提で使われます。

r.setW(5);
r.setH(2);
assert(r.area() == 10);

ところが Square は、

- width を変えると height も変わる

必要があります。

つまり利用側の期待が壊れます。

結果として、

「Rectangle として扱えるはずなのに、
実際は同じように振る舞わない」

状態になります。

これがLSP違反です。

本質的には、

「継承関係」より
「振る舞いの契約」が重要

という話です。

つまりLSPは、

- 同じインターフェース
- 同じ期待
- 同じ意味

で扱えることを要求しています。

だからLSPは、

「型の一致」ではなく、“利用者視点での一貫性” を守る原則と言えます。

「サブクラスが親と完全一致しろ」ではなく、「利用者から見た意味を壊すな」という原則。


Python の機械学習ライブラリは、LSPの感覚をかなり実践的に体現しているように思える。

たとえば scikit-learn では、

model.fit(X, y)
model.predict(X)

という共通インターフェースがあります。

利用者は、

- RandomForest
- SVM
- LogisticRegression
- XGBoost風ラッパー

などを、

ほぼ同じように扱えます。

ここで重要なのは、

「内部アルゴリズムが同じ」

ことではありません。

むしろ内部は全然違います。

でも利用者から見ると、

- fit したら学習される
- predict したら予測が返る
- 入出力形式が一定
- 想定された契約を守る

という期待が保たれています。

これがLSP的です。

逆にLSP違反っぽいのは、

predict()

したら、

- たまに shape が違う
- モデルによって戻り値形式が違う
- 学習済みでも predict 不可
- fit が破壊的挙動をする

みたいなケースです。

LSPはかなり実務的には、

「抽象化したなら、その抽象としてちゃんと扱えるようにしろ」

という原則と解釈できる。
違反していると抽象が壊れて利用者側でif文での分岐が必要になって処理をわけないといけなくなる。

だからClean Architecture文脈では、

- Plugin
- DI
- Interface
- Strategy Pattern

あたりとかなり強く結びついている。


ISP（Interface Segregation Principle：インターフェース分離の原則）は、

「使わないものに依存するな」という原則です。

かなり本質的には、「必要最小限だけ知れ」という話です。

たとえば、

interface OPS {
  op1()
  op2()
  op3()
}

があって、

- User1 は op1 しか使わない
- User2 は op2 しか使わない

のに、
全員が OPS に依存していると、

op2 を変更しただけで、
User1 まで影響を受ける可能性があります。

つまり、

「関係ない変更に巻き込まれる」

状態です。

なのでISPでは、

U1Ops
U2Ops
U3Ops

のように分割して、

必要なものだけ依存させます。

これは単なる“interface分割テク”ではなく、
本質は、

「不要な結合を減らす」

ことです。


System → Framework → Database


という依存があって、

Framework が使っていないDB機能の変更なのに、
System 全体再デプロイになる。

あるいは、

使ってもいない機能の障害で
システムが巻き込まれる。

これもISP問題です。

つまりISPは、

「巨大な塊に依存すると、
不要な変更・障害・再ビルドまで背負い込む」

という警告なんです。

実務だとかなりよくあります。

たとえば、

- utils.ts が巨大
- common package が肥大化
- SDK全部import
- React component library全部依存
- AWS SDKフル導入

みたいな状態。

すると、

- 小変更で全体再build
- deploy ripple
- bundle肥大
- unrelated bug contamination

が起きます。

なのでISPは実務的には、

「必要な面だけ見ろ」

「不要な責任まで背負うな」

「依存は細く保て」

という原則として理解するとかなりわかりやすい。



DIP（Dependency Inversion Principle：依存関係逆転の原則）は、

「具体ではなく、抽象に依存しろ」

という原則です。

かなり重要なのは、
“依存方向を制御する” という考え方です。

普通に書くと、


BusinessLogic -> MySQL
BusinessLogic -> StripeAPI
BusinessLogic -> OpenAIClient

みたいに、
ビジネスロジックが具体実装へ直接依存します。

すると、

- DB変更
- API変更
- SDK変更

が全部ビジネスロジックへ波及します。

DIPではこれを逆転させます。


BusinessLogic -> PaymentGateway(interface)
StripePaymentGateway -> PaymentGateway


つまり、

高レベルポリシー（業務ルール）
↓
抽象(interface)
↑
低レベル実装(DB/API)

という形にする。

するとビジネスロジックは、

「決済できる」

という抽象しか知らなくてよくなります。

StripeなのかPayPalなのかは知らない。

これが「依存関係逆転」です。

本来、

Business -> Detail
だった依存を、
Detail -> Abstraction <- Business

へ変える。

だからDIPは、
OOの「ポリモーフィズムの力」を
アーキテクチャに適用したものとも言えます。

この章でかなり重要なのは、

「抽象は安定しやすく、
具体実装は変わりやすい」

という話です。

たとえば、

- MySQL
- AWS SDK
- UI framework
- external API

は変わりやすい一方、

saveUser()
chargePayment()
generateReport()

みたいな業務概念は比較的安定しています。

だから“安定したもの”を中心に依存を組む。

これがClean Architectureの核心です。

そしてDIPを実現するために出てくるのが、

- Interface
- Abstract Factory
- DI
- Plugin Architecture

です。

特にFactoryは、

service = ConcreteImpl()

みたいな “new依存” を隔離するためにあります。

なぜなら、オブジェクト生成そのものが具体実装依存だからです。

なので最終的にDIPは、「変わりやすい詳細を、変わりにくい中心から切り離せ」という原則。

Clean Architecture全体は、ほぼこの思想の巨大版。


コンポーネントは「独立してデプロイできる最小単位」

jar、DLL、gem、shared library などがそれにあたる

重要なのは、

・独立して開発できる
・独立して差し替えできる
・変更の影響を局所化できる

こと

ソフトウェアの歴史は、

巨大な一枚岩
↓
分離コンパイル
↓
リンク
↓
動的リンク
↓
プラグイン化

という流れで進化してきた

昔は全部まとめてコンパイルしていたため、
システム巨大化とともに開発効率が悪化した

その後、

・linker
・DLL
・jar

などによって、
「必要な部品だけ組み合わせる」構造になった

現代アーキテクチャの本質は、

「システムを交換可能な部品として分割すること」

にある

OOやDIPによって、

・ビジネスルール
・UI
・DB
・外部サービス

を分離し、
UIやDBをプラグイン化できるようになった

つまりコンポーネント設計とは、

「どこを安定させ、どこを変更可能にするか」

を決める設計

Clean Architecture全体は、

「変わりやすいものを外側へ追い出し、本質的なルールを中心に守る」

という思想で統一されている。


コンポーネント凝集（Component Cohesion）は、

「どのクラスを同じコンポーネントに入れるべきか」

を決めるための原則。

主に3つある。

・REP（Reuse/Release Equivalence Principle）
・CCP（Common Closure Principle）
・CRP（Common Reuse Principle）


REP（再利用・リリース等価原則）

「再利用の単位 = リリースの単位」

つまり、一緒に再利用されるものは、一緒にバージョン管理・リリースされるべき。

コンポーネントは単なる寄せ集めではなく、

・同じ目的
・同じ責務
・同じ文脈

を共有している必要がある。

利用者から見ても、「このまとまりは自然」と思える必要がある。


CCP（共通閉鎖原則）

「同じ理由で同じタイミングに変更されるものを集める」

SRPのコンポーネント版。

もし複数のクラスがいつも一緒に変更されるなら、同じコンポーネントに置く。

逆に、

・変更理由が違う
・変更タイミングが違う

なら分ける。

目的は変更影響の局所化。

変更時に、関係ないコンポーネントまで再デプロイしなくて済む。

要するに、「一緒に変わるものは一緒に置け」という原則。


CRP（共通再利用原則）

「必要ないものに依存させるな」

ISPのコンポーネント版。

もしあるコンポーネントを使うことで、

・本当は不要なクラス
・関係ない機能

まで依存してしまうなら、そのコンポーネント分割は悪い。

つまり、「一緒に再利用されないものを同じコンポーネントに入れるな」という話。


この3つをまとめると、

REP
→ 「自然なまとまりを作れ」

CCP
→ 「一緒に変更されるものを集めろ」

CRP
→ 「一緒に使われないものは分けろ」

になる。

そして核心は、「変更」と「依存」をどう制御するか。

Clean Architecture全体はずっと、

・変更を閉じ込める
・不要な依存を減らす
・本質を守る

ための設計原則を説明している。


コンポーネント凝集の「緊張ダイアグラム」は、

REP・CCP・CRPの3つが互いにトレードオフ関係にあることを示している。


まず3つの性質の方向性

・REP（再利用・リリース等価原則）
→ コンポーネントは再利用単位としてまとまるべき
→ 大きくなる方向

・CCP（共通閉鎖原則）
→ 同じ理由で変更されるものをまとめる
→ 大きくなる方向

・CRP（共通再利用原則）
→ 不要な依存を排除する
→ 小さく分割する方向


この3つは同時に最大化できない。

・REPとCCPを強くすると
→ コンポーネントが肥大化しやすい
→ 変更は局所化されるが、無関係な依存も増える

・CRPを強くすると
→ コンポーネントは細かくなる
→ 必要なものだけ依存できるが、分割しすぎると管理が難しくなる


重要なのは「バランス」

良いアーキテクトは、

・プロジェクト初期
→ CCP優先（変更のしやすさ・開発効率重視）
→ 再利用はまだ重視しない

・成熟期
→ REPが重要になる（他プロジェクトでの再利用が増える）
→ コンポーネントは安定してくる

・常にCRPは意識
→ 不要な依存を避ける

つまり時間とともに最適解は変わる。

・初期は開発しやすさ優先で分割しやすい構造
・成長すると再利用しやすい安定した構造へ移行

コンポーネント設計は固定の正解ではなく、「変更・再利用・依存のバランス調整」であり、
その最適点はプロジェクトの成熟度によって動く


コンポーネント結合（Component Coupling）の基本

コンポーネント同士の関係をどう設計するかの原則群で、開発しやすさと設計の健全性のバランスを扱う。

■ Acyclic Dependencies Principle（非循環依存の原則）

コンポーネント間の依存関係に循環を作らないことが重要。

循環依存があると、あるコンポーネントの変更が連鎖的に広がり、全体が密結合化してビルド・テスト・変更が困難になる。

■ 問題の本質（循環依存の弊害）

- 複数チームが同じコンポーネント群を同時に更新する必要が出る
- 変更の影響範囲が予測不能になる
- テストに必要な依存関係が増えて単体テストが成立しにくくなる
- ビルド順序が曖昧または不可能になる
- 実質的に複数コンポーネントが1つに融合した状態になる

■ 解決アプローチ

コンポーネントを「リリース可能単位」に分割し、明確な依存方向を持たせる。

- 各コンポーネントは独立してビルド・リリース可能
- 他コンポーネントは安定版を参照する
- 新しいバージョンの採用タイミングは利用側が決定

■ 依存構造の理想形

依存関係は有向グラフになり、必ず循環しない形（DAG）にする。

- 上位コンポーネント → 下位コンポーネントの方向に依存
- どのコンポーネントから辿っても元に戻らない構造

■ 効果

- 変更の影響範囲が局所化される
- ビルド順序が明確になる
- テストが独立して行える
- チーム間の干渉が減る
- リリースの安定性が上がる

■ 循環がある場合の本質的問題

循環依存は「複数コンポーネントが論理的に一体化してしまう状態」を作るため、分割の意味が崩れる。結果として変更・テスト・リリースの独立性が失われる。


■ 循環依存は必ず壊せる

コンポーネント間に循環（A→B→C→A）があっても、必ずDAG（非循環構造）に戻せる。

方法は主に2つ。


■ 方法1：依存関係逆転（DIPの適用）

- インターフェースを導入する
- 依存方向を反転させる
- 抽象に依存させることで循環を切る

結果：

- 具体同士の依存が消える
- 片方向の依存になる


■ 方法2：共通コンポーネントの抽出

- 両方が依存している要素を切り出す
- 新しいコンポーネントに移す
- 両者がそこに依存する形にする

結果：

- 重複依存を中央に集約
- 依存関係が整理される


■ 「ジッター（Jitter）」の意味

設計が進むにつれて：

- コンポーネント構造は固定されない
- 変更のたびに再編が起こる
- 新しい依存や分離が発生する

つまり：

コンポーネント構造は揺れながら成長する


■ 重要な結論：トップダウン設計はできない

コンポーネント構造は最初から設計するものではない。

理由：

- 初期段階では何が変化するか分からない
- 再利用単位も見えていない
- 依存関係も未成熟

そのため：

コードが育つ過程で自然に形が決まる


■ コンポーネント設計の本質

コンポーネント依存構造は「機能設計」ではない。

では何かというと：

- ビルド可能性の地図
- 保守性の構造
- 変更耐性の設計


■ 何で構造が決まるか

主にこの3つで変形する：

1. SRP / CCP
    　→ 変更理由ごとに分離・集約
2. CRP
    　→ 再利用単位でまとめる／分離
3. ADP
    　→ 循環が出たら壊す（DAG維持）

■ 重要な思想

- UI変更とビジネスルールは混ぜない
- 不安定なものは安定したものに依存させない
- 変更の波を局所化する


■ 最終的な結論

コンポーネント構造は：

- 最初に設計するものではない
- 機能の設計図でもない
- 成長しながら最適化される依存マップ

そして常に：変化・再利用・循環排除のバランスで進化する構造


Stable Dependencies Principle（SDP）の要点まとめ


■ 基本原則

依存は「より安定した方向」に向けること。

- 不安定なもの → 安定したものに依存する
- 安定したもの → 不安定なものに依存しない


■ 安定性とは何か

ここでいう安定性は「変わらないこと」ではない。

本質はこれ：

- 変更するのにどれだけコストがかかるか


■ 安定する理由

あるコンポーネントが安定する条件：

- 他の多くのコンポーネントから依存されている（Fan-inが多い）

→ 変えると影響範囲が大きすぎるため変更しにくい


■ 不安定な状態

逆に不安定なコンポーネントは：

- どこからも使われていない（Fan-inが少ない）
- 他の多くに依存している（Fan-outが多い）

→ 自由に変えやすいが、外部変化の影響も受けやすい


■ 安定性の指標（I）

不安定度は次で表される：

I = Fan-out / (Fan-in + Fan-out)

- 0 → 最も安定（依存されるが依存しない）
- 1 → 最も不安定（依存するが依存されない）


■ 理想構造

システム全体の設計はこうなる：

- 上：不安定（変更しやすい）
- 下：安定（変更しにくい）

依存は常に「上 → 下」に流れる


■ 重要な設計原則

- 不安定にしたいコンポーネントは、安定したものに依存させない
- 安定したものに依存させると、安定側まで変更しにくくなる


■ なぜ問題が起きるか

あるコンポーネントを「変更しやすく設計した」としても、

- 別のコンポーネントがそれに依存した瞬間
- そのコンポーネントは“変更しにくい存在”に変わる


■ 解決方法（DIPの活用）

循環や不適切な依存はこうして解消する：

- インターフェースを切り出す
- 抽象に依存させる
- 依存方向を反転させる

結果：

- 安定した抽象に依存
- 不安定な実装はその背後に隠れる


■ 抽象コンポーネントの役割

インターフェースだけのコンポーネントは：

- 実装を持たない
- 非常に安定している
- 多くの不安定な実装の依存先になる


■ 本質まとめ

SDPの核心はこれ：依存は「壊れにくい方向」に向けることで、変更の波及を制御する設計原則



コンポーネント設計の本質

コンポーネント設計は「クラスをどうまとめるか」ではなく、
「変更・再利用・依存関係をどう制御するか」の問題。

そのために3つの指針（REP / CCP / CRP）があるが、互いにトレードオフになる。


3つのコンポーネント凝集原則

REP（再利用とリリースの等価性）

再利用される単位はリリース単位であるべき。

つまり、

- 再利用したいなら「独立したバージョン」として配布できる必要がある
- ただのクラスの寄せ集めではダメ
- “一緒にリリースされる意味がある塊”であることが重要


CCP（共通閉鎖原則）

同じ理由・同じタイミングで変更されるものは同じコンポーネントにまとめる。

ポイント：

- 変更理由が違うものは分離する
- 変更が1箇所に閉じるようにする
- SRPの「クラス版」をコンポーネントに拡張したもの

狙い：

- 変更影響を局所化
- リリース単位を小さくする


CRP（共通再利用原則）

使わないものに依存させるな。

ポイント：

- 一緒に再利用されるものだけを同じコンポーネントに入れる
- 使わないクラスが混ざると依存コストが増える
- 不要な変更や再コンパイルを誘発する


重要な構造：3原則の緊張関係

この3つは同時に最大化できない。

- REP / CCP → コンポーネントは「大きくなる方向」
- CRP → コンポーネントは「小さくなる方向」

結果として：

- まとめすぎると変更コストが上がる
- 分けすぎると再利用性が落ちる

設計とはこのバランス調整になる。


コンポーネントCouplingの核心（依存関係設計）

ADP（循環依存禁止）

コンポーネント依存グラフは循環させない。

理由：

- ビルド順序が壊れる
- 変更影響が全体に波及する
- 実質「全部が1つの巨大コンポーネント」になる

解決：

- 依存逆転（DIP）
- 共通コンポーネント抽出


SDP（安定依存原則）

依存は「安定している方向」に向ける。

意味：

- 変更されにくいものに依存するのが正しい
- 変更されやすいものに依存すると全体が壊れる

安定性の本質：

- 多く依存されるほど安定
- 多く依存しているほど変更が難しい


SAP（安定抽象原則）

安定しているものほど抽象的であるべき。

理由：

- 安定＝変更されにくい
- 抽象＝拡張できる
- つまり「安定しているなら拡張できる形にする必要がある」

結論：

- 安定コンポーネント → interface / abstract中心
- 不安定コンポーネント → concrete中心


重要な統合概念

SDP + SAP = コンポーネントレベルのDIP

つまり：

- 依存は安定へ向かう（SDP）
- 安定は抽象へ向かう（SAP）
    → 結果として依存は「抽象へ向かう」


ゾーン理論（設計の良し悪し）

Zone of Pain（痛みの領域）

- 安定 + 非抽象（I低 + A低）
- 変更しにくいのに柔軟性がない
- DBスキーマなどが典型

問題：

- 修正が非常に高コスト
- 影響範囲が広い


Zone of Uselessness（無駄領域）

- 抽象的なのに誰も依存しない（A高 + I高）
- 使われない抽象が残る

問題：

- 設計上のゴミになる
- 意味のない抽象化


Main Sequence（理想線）

- A + I ≈ 1 のライン

意味：

- 抽象度と安定性のバランスが取れている
- 役割に応じた健全な構造


距離指標（設計評価）

D = |A + I - 1|

- 0に近い → 良い設計
- 大きい → バランス崩壊


全体の本質

コンポーネント設計の本質はこれ：

- 変更理由を分離する（CCP）
- 再利用単位を揃える（REP）
- 不要な依存を排除する（CRP）
- 依存方向を安定へ揃える（SDP）
- 安定を抽象化する（SAP）
- 循環を排除する（ADP）

つまり「変更の伝播を制御する構造設計」になる


まずアーキテクチャは見た目の構造ではなく、システムの“変更しやすさ”を決める設計である。システムを機能で分けることではなく、開発・デプロイ・運用・保守を長期的に成立させるための形を決める行為になる。つまり正しく動くことそのものよりも、「変化に耐えること」「変更のコストを下げること」が主目的になる。


そのために最も重要な考え方が「詳細と方針の分離」になる。

ビジネスルールや判断基準のような中核部分が“方針”であり、データベース、フレームワーク、UI、通信方式などは“詳細”として扱う。設計の目的は、方針が詳細に依存しない構造を作ることにある。これによって、データベースやUI技術などの選択を後から変更できる状態を維持できる。


この構造を支える実践的な考え方がいくつかある。

開発の観点では、チームが分割されるとコンポーネント単位で責任を持つ構造が自然に生まれる。運用の観点では、デプロイ単位として独立して更新できることが重要になる。保守の観点では、変更が局所化されていることがコストを大きく下げる。

つまりコンポーネント設計は「作りやすさ」ではなく「変更の影響範囲をどう制御するか」の問題になる。


さらに重要なのが依存関係の管理になる。

依存関係にループがあると、変更が連鎖して全体が一体化してしまい、部分的な変更やテストが不可能になる。これを避けるために、依存関係は常に一方向（非循環）である必要がある。

依存の向きは「安定しているものへ向かう」ことが基本になる。安定とは、他から多く依存されている状態であり、変更コストが高い状態を意味する。逆に不安定なものは変更しやすいが、他に依存してはいけない。


ここに抽象度の考え方が加わる。

安定しているものは変更されにくいので、同時に抽象的であるべきになる。抽象的であれば、具体実装を変えることで拡張できるからである。逆に不安定なものは具体的で良い。

この関係によって「安定しているものほど抽象的であるべき」という構造が成立する。


最終的に目指すのは、安定性と抽象度のバランスが取れた配置になる。

どちらかに寄りすぎると問題が起きる。安定すぎて具体的すぎると変更不能になる。抽象的すぎて依存されないと役割がなくなる。ちょうど良い位置は、その間の対角線上に近い領域になる。


まとめるとこの章は次の構造になっている。

アーキテクチャは機能設計ではなく変更設計である。
そのために方針と詳細を分離する。
その上で依存関係を一方向に保つ。
さらに安定性と抽象性を一致させて配置する。
結果として、将来の変更を局所化できる構造ができる。


この章の本質は「アーキテクチャは何を固定し、何を可変として残すか」という一点に集約される。


まず強調されるのは、良いアーキテクチャは4つの独立性を同時に満たす必要があるという点になる。ユースケースの表現、運用性能、開発のしやすさ、デプロイのしやすさ。この4つは別々の要求であり、それぞれ独立して満たされるべき対象になる。


ユースケースの独立性では、システムの構造そのものが「何をするものか」を自然に語っている状態が理想になる。例えばショッピングシステムなら、コード構造を見ただけでカート追加や削除などの機能が見える状態が望ましい。機能が隠れているのではなく、構造として露出している状態になる。


運用の独立性では、性能要件に対して構造を柔軟にできることが重要になる。高負荷なら並列化、小規模ならモノリスというように、同じ設計が異なる実行形態に対応できる必要がある。そのためには、最初から実行方式（プロセス・スレッド・サービス）を固定しない構造が必要になる。


開発の独立性では、チーム分割とアーキテクチャが一致している必要がある。依存関係が整理されていれば、チーム同士が干渉せずに並行開発できる。これはコンウェイの法則と密接に関係し、組織構造がそのままシステム構造に反映されるため、構造設計は組織設計でもあることになる。


デプロイの独立性では、できる限り「一回の操作で動く状態」を目指すことが重要になる。複雑な手動設定や依存調整が必要な状態は望ましくなく、コンポーネントが適切に分離されていれば、ビルド後すぐに動かせる状態が実現できる。


これらすべてに共通する考え方が「選択肢をできるだけ長く残す」という設計思想になる。つまりアーキテクチャとは決定ではなく保留の設計であり、早期に技術的選択を固定しないことが重要になる。


そのための実践方法が「水平分割と垂直分割の両立」になる。

横方向ではUI、ドメインロジック、データベースといった変更理由の異なる要素を分離する。縦方向ではユースケース単位で機能を切り出し、それぞれが横方向のレイヤーを貫通する構造になる。

この二軸構造によって、新しいユースケース追加が既存機能に影響しにくくなる。


さらに重要なのが「モードの分離」という考え方になる。

コンポーネントの分離は段階がある。
ソースレベル（同一プロセス内の分離）、
デプロイレベル（ライブラリ単位の分離）、
サービスレベル（ネットワーク分離）。

どのレベルを選ぶかは固定ではなく、システムの成長に応じて変わる可能性がある。そのため最初からマイクロサービスにするのではなく、必要に応じて段階的に上げられる構造にしておくことが重要になる。


この設計思想の裏にある重要な誤解への注意もある。

似ているからといって機能や構造を統合するのは危険になる。今は同じに見えても、時間とともに変化速度や理由が異なるため、結果的に別物になる可能性が高い。逆に安易な共通化は将来の分離コストを増大させる。


まとめるとこの章は次の構造になる。

アーキテクチャは機能実装ではなく「独立性の設計」である。
ユースケース・運用・開発・デプロイをそれぞれ独立させる。
そのために水平レイヤーと垂直ユースケースを分離する。
さらに実行形態のモード変更を将来の選択肢として残す。
結果として、変化に適応できる構造を維持する。



結論から言うと、「アーキテクチャ＝境界をどこに引くか」で、DDDとClean Architectureはその“境界の引き方の哲学”が少し違うだけ。


1. 共通している本質（DDDもClean Architectureも同じ）

両方とも共通しているのはこれ：

システムは「変わる理由の違うもの」を分離するために境界を引く

分け方の代表はこうなる：

- ビジネスルール（変わりにくい・価値の中心）
- UI（変わりやすい）
- DB・外部API（変わりやすい・詳細）

そして重要なのはこれ：

ビジネスルールを中心にして、外側の都合から守る

つまり構造としてはどちらも

外側（UI / DB / FW） → 内側（ドメイン）

という依存方向になる。


2. Clean Architectureの思想（ロバート・マーチン系）

Clean Architectureはかなり明確に「構造モデル」を定義している。

中心はこれ：

- Use Case（アプリケーションの振る舞い）
- Entities（ドメインルール）

外側：

- UI
- DB
- Framework

そしてルールは一貫してこれ：

依存は必ず内側へ向かう

さらに重要なのが「境界＝インターフェース」という考え方。

- DBはインターフェースの裏に隠す
- UIもインターフェース越し
- 変更可能なものは全部外側

イメージは：

UI → Use Case → Entity ← DB


特徴は：

- 構造がかなり明示的
- レイヤー設計が強い
- 「依存方向」が設計の中心


3. DDDの思想（エヴァンス系）

DDDはClean Architectureよりも抽象度が高い。

中心はこれ：

複雑な業務領域を「モデル」で表現すること

DDDの本質はアーキテクチャではなく：

- ドメインとは何か
- モデルとは何か
- 言語を揃える（Ubiquitous Language）

そして設計の単位は：

- Entity（同一性のあるもの）
- Value Object（値）
- Aggregate（整合性境界）
- Domain Service（ルール）

DDDはこういう問いに答える：

「この業務の本質的なルールは何か？」


4. Clean Architectureとの違い（ここが核心）

整理すると違いはここ：

■ Clean Architecture

構造の話

- システムをどう分割するか
- 依存方向をどうするか
- UI/DBをどう隔離するか

→ “システム設計の物理構造”


■ DDD

意味の話

- 業務の本質をどうモデル化するか
- ルールをどこに置くか
- ドメインの境界はどこか

→ “現実世界の意味構造”


5. 関係を一言でまとめると

かなり本質的に言うとこうなる：

- DDD = 「何を作るべきか（意味の設計）」
- Clean Architecture = 「どう壊れにくく配置するか（構造の設計）」


6. 直感的な統合イメージ

実務ではこう重なる：

- DDDで「ドメインの境界」を決める
- Clean Architectureで「依存の境界」を守る

つまり：

DDD → 内側の設計
Clean Architecture → 外側との接続設計

7. 重要な誤解ポイント

よくあるズレ：

- DDD＝アーキテクチャだと思う
- Clean Architecture＝ドメイン設計だと思う

実際は逆寄りで：

- DDDは“中身の意味設計”
- Clean Architectureは“包み方の設計”


ソフトウェアアーキテクチャ＝「境界の種類」と「依存の向き」の設計

その上で、この章は“境界の階層構造”を整理している。


1. 境界の本質（全部に共通する1つのルール）

境界の形が何であれ共通しているルールはこれ：

境界＝依存関係を片方向に固定するための線

そして重要なのは2つだけ：

- 依存は高レベル（ビジネス）へ向かう
- 境界を跨ぐときにコストが発生する


2. 境界は「物理的な強さ」で段階がある

この章の中心はこれ：

境界は1種類ではなく、コストと強度のグラデーションになっている

弱い → 強い順に並べるとこうなる：


① モノリス（ソースレベル境界）

- 同じプロセス・同じメモリ
- 関数呼び出しで跨ぐ
- 最も軽い境界

特徴：

- 依存はコード構造だけで制御
- コンパイル単位で分離
- ポリモーフィズムが重要

ポイント：

境界は「見えないが存在する」


② デプロイメント境界（jar / dll）

- 同じプロセス
- ただし別パッケージとして配布

特徴：

- 依存はビルド単位で分離
- 動的リンクなどが使われる
- モノリスとほぼ同じ実行環境

違いは：

「配布単位」が分かれる


③ スレッド（境界ではないが重要）

- 実行の並列性の単位
- アーキテクチャ境界ではない

役割：

- どの順番で動くかを決めるだけ
- 構造ではなくスケジューリング


④ ローカルプロセス境界

- 別プロセス（メモリ分離あり）
- IPC（ソケットなど）で通信

特徴：

- コスト：中
- 独立性：高い
- 通信は重い

ここで重要になる制約：

チャッティな設計は破綻する


⑤ サービス境界（最強）

- ネットワーク越し
- 完全独立デプロイ

特徴：

- 最も遅い
- 最も独立性が高い
- 失敗モードが増える

ルール：

URIなどの具体依存を持つな


3. 重要な核心（全部の共通ルール）

どの境界でも同じ設計原則：

依存は必ず「上位（ビジネスルール）」へ向かう

つまり：

- UI → ビジネスルール
- DB → ビジネスルール
- サービス実装 → ビジネスルール


4. 境界の本質は「コストの違い」

境界ごとの違いはこれ：


境界　　　　　　コスト　　独立性
関数呼び出し　　　低　　　 低
jar/dll　　　　低〜中　　中
プロセス　　　　　中　　　 高
サービス　　　　　高　　　最高

そして設計の核心はこれ：

コストが高い境界ほど、分離の意味が強い


5. 重要な設計判断

この章が言いたい現実的な結論：

最初からサービス分割するな

理由：

- コストが高すぎる
- 変更が遅くなる
- 分割粒度が粗くなる

代わりに：

- まずはソースレベルで分離
- 必要になったら上のレイヤへ上げる


6. FitNesseの話の意味（超重要）

あの話の本質はこれ：

境界を早く引けば引くほど「未来の選択肢」が増える

- DBを後から決められる
- UIを後から変えられる
- サービス化も後からできる

この章の本質はこれ：アーキテクチャとは「どのコストで境界を引くかの設計」である


■ この章の核心

ソフトウェアは「ポリシー（意思決定）の階層構造」でできている

つまりプログラムとは
「何をどう変換するか」というルールの集まり。


■ レベルの定義

レベル＝入力・出力からの距離

- 低レベル：UI・DB・デバイスなど入出力に近い
- 高レベル：ビジネスルール・ドメインロジックなど中心的判断

重要なのは「物理的な位置」ではなく
「意味的な距離」


■ 重要な設計ルール

データの流れと依存方向は一致させない

- データは上下どちらにも流れる
- 依存は必ず「高レベル」へ向ける

理由：
低レベルは変わりやすく、高レベルは変わりにくいから


■ 良い設計の形

- 高レベル（ルール・判断）
- 中間（アプリケーションの制御）
- 低レベル（UI・DB・外部入出力）

構造としては分離されるが
依存は常に「低 → 高」に向く


■ 悪い設計の本質

高レベルが低レベルを直接呼ぶ構造

問題：

- UI変更でビジネスロジックが壊れる
- DB変更がドメインに波及する
- 再利用できない


■ 良い設計の本質

高レベルがインターフェースを定義し
低レベルがそれを実装する

結果：
低レベルが高レベルに依存する構造になる


■ なぜこうするのか

理由はシンプル：

変わりやすいもの（IO）から
変わりにくいもの（ビジネスルール）を守るため


■ Clean Architectureとの関係

この章はそのままClean Architectureの理論基盤

対応関係：

- 高レベルポリシー → Use Case / Entity
- 低レベル詳細 → UI / DB / Framework
- 依存方向 → 内側へ


■ DDDとの関係

- DDDは「何が重要なルールか」を定義
- Policy & Levelは「そのルールをどこに置くか」を定義



■ 一言でまとめると

アーキテクチャとは「変化の理由が違うものをレベルで分け、依存方向を固定する設計」

ビジネスルールとは何か

ソフトウェアの中心は「ビジネスルール」であり、これは会社が利益を得たり損失を防いだりするためのルールそのもの。

重要なのは「コンピュータがなくても成立するルール」と「コンピュータがあるから成立するルール」を分けて考えること。


① クリティカルビジネスルール（Entity）

これはビジネスそのものの核になるルール。

例えば銀行なら：
・利息の計算
・ローン残高の扱い
・返済スケジュール

これらはシステムがなくても存在する「本質的なルール」。

そしてそれに必要なデータ（残高・金利など）もセットで存在する。

この「ルール＋データのまとまり」が Entity。

特徴は次の通り：
・UIに依存しない
・DBに依存しない
・フレームワークにも依存しない
・どんなシステムでも再利用できる

つまり「ビジネスの本体」だけを切り出したもの。


② ユースケース（アプリケーションルール）

こちらは「システムとしてどう動くか」を決めるルール。

例：
・顧客情報を入力したあとでないとローン審査に進めない
・信用スコアが一定以上でないと処理できない

これは現実の業務ルールではなく、
「このアプリケーションでの操作手順」を定義している。

特徴：
・Entityを呼び出して使う側
・UIやDBの中間にある
・アプリごとに変わる

つまり「業務の流れの制御役」。


Entityとユースケースの関係

関係は明確に一方向：

ユースケース → Entity を使う
Entity → ユースケースを知らない

理由は単純で、Entityのほうが本質的で再利用可能だから。

ユースケースはアプリごとに変わるため、Entityより低いレベルに置かれる。


リクエスト・レスポンスモデル

ユースケースは入力と出力を扱うが、
その中身はUIやDBに依存させてはいけない。

そのため：

・入力は Request Model
・出力は Response Model

これらは完全に独立したデータ構造にする。

ここで重要なのは：Entityを直接混ぜないこと。

理由：
・寿命が違う（変わるタイミングが違う）
・責務が違う
・依存が増えて設計が崩れる


レベルの考え方

レベルとは「入力・出力からの距離」。

低レベル：
・UI
・DB
・外部システム

高レベル：
・Entity（ビジネスそのもの）
・コアロジック

設計の基本はこれ：

低レベルは高レベルに依存する
高レベルは低レベルを知らない


まとめ（構造の本質）

ソフトウェアは次の2層に分解できる：

・変わりにくい本質（Entity）
・変わりやすい操作（Use Case / UI / DB）

そして設計の目的はこれ：「本質を中心に固定し、周辺を差し替え可能にすること」



SCREAMING ARCHITECTURE（叫ぶアーキテクチャ）

ソフトウェアの構造は「何のシステムなのか」を一目で伝えるべきだという考え方。

つまり：

・フォルダ構造やコード構成を見た瞬間に
・そのシステムの目的が分かること

例：
・病院システム → 医療業務の構造が見える
・会計システム → 取引・勘定の構造が見える

理想：
「使っているフレームワーク名」ではなく
「ビジネスの意味」が見えること


アーキテクチャの中心は“ユースケース”

重要な主張はこれ：

アーキテクチャはフレームワークではなくユースケースで語られるべき

理由：
・RailsやSpring中心だと設計が技術依存になる
・本来は「何をするシステムか」が中心

つまり：
構造は「業務の流れ」に合わせるべきであって
技術の都合に従うべきではない


Webはアーキテクチャではない

Webは単なる配送手段（IO）

・UIの一種
・入力と出力の手段

そのため：
・Webに合わせて設計を決めるのは逆転している
・コンソール・Web・APIは差し替え可能であるべき


フレームワークは主役ではない

フレームワークの問題点：

・強い思想を持っている
・システム全体を支配しようとする

設計の正しい姿勢：
・フレームワークに従うのではなく
・フレームワークを「差し替え可能な道具」にする


テスト可能な設計

良いアーキテクチャの条件：

・DBなしでテストできる
・Webなしでテストできる
・UIなしでテストできる

理由：
・ビジネスロジックは純粋であるべきだから


クリーンアーキテクチャの構造

4層構造：

① Entities（最も重要）
・ビジネスの本質ルール
・ほぼ変わらない

② Use Cases
・アプリ固有の業務フロー
・Entityを操作する

③ Interface Adapters
・UIやDB用にデータ変換
・MVCもここに含まれる

④ Frameworks & Drivers
・Web / DB / 外部サービス
・最も外側の詳細


依存のルール（最重要）

依存は必ず内側へ向かう

・外側 → 内側はOK
・内側 → 外側は禁止

意味：
・ビジネスは技術を知らない
・技術はビジネスに従う


データの流れ

典型的な流れ：

Web → Controller → Use Case → Entity → DB

戻り：

Entity → Use Case → Presenter → View

特徴：
・途中でデータ形式を変換する
・外部形式を内部に持ち込まない


ViewModel / DTOの役割

・Use Caseは純粋なデータだけ扱う
・UI用の形はPresenterが作る

重要：
EntityをUIに直接渡さない

理由：
・責務が違う
・変更理由が違う


Screaming Architectureの本質

「これは何のシステムか？」ではなく「これはRailsシステムか？」でもない

システムを見た瞬間にこう聞こえるべき：

理想：
・技術ではなく意味が見える
・フレームワークではなくドメインが見える


最終まとめ

良いアーキテクチャはこれを実現する：

・ビジネスを中心に置く
・技術は外側に追いやる
・依存は必ず内向き
・UIやDBは差し替え可能にする

結果として：
システムは「技術の集合」ではなく
「業務の構造そのもの」として見えるようになる


HUMBLE OBJECT（控えめなオブジェクト）とは

テストしにくい処理とテストしやすい処理を分離する設計パターン。

- テストしにくい部分：UI操作、DBアクセス、外部通信など
- テストしやすい部分：データ加工、ビジネスルール、計算

この2つを別のコンポーネントに分ける。


PRESENTERS と VIEW

VIEW（控えめな側）

- 画面表示だけを担当
- データ加工はしない
- ViewModelの内容をそのまま画面に表示するだけ

PRESENTER（テスト可能な側）

- 表示用データに変換する
- 例：
    - Date → 表示用文字列
    - Currency → フォーマット済み文字列
    - 状態 → true/falseフラグ

ViewModel

- 文字列・boolean・enumだけで構成
- UI表示専用のデータ構造

結果として：

- UIロジックはPresenter側に集まる
- Viewは単純化される


DATABASE GATEWAY

- Use CaseとDBの間にインターフェースを置く
- SQLをUse Caseに書かない

構造：

- Use Case → Gateway（インターフェース） → DB実装

特徴：

- Gatewayは抽象（テスト対象）
- DB実装はHumble Object（置き換え可能）

例：

- getLastNamesOfUsersWhoLoggedInAfter(date)


DATA MAPPER（ORMの位置づけ）

ORMの本質：

- SQL結果 → データ構造への変換

ポイント：

- ORMは「オブジェクト」ではなく「データ変換器」
- 役割はDBレイヤー側にある

つまり：

- Use Case層はORMを知らない
- DB層でデータ変換を担当


SERVICE LISTENER（外部サービス連携）

外部サービスとの境界も同じ構造：

送信側

- 内部データ → 単純データ構造 → 外部サービス

受信側

- 外部データ → 単純データ構造 → アプリ内部

ポイント：

- 境界では必ず「単純データ構造」を使う
- 外部通信はHumble Object側に閉じる


全体構造

Humble Objectパターンは境界設計そのもの：

- テストしやすい部分を内側に残す
- 外部依存は外側に押し出す
- 境界ではデータ変換だけを行う
- ビジネスロジックは外部から独立させる


PARTIAL BOUNDARIES（部分的な境界）

完全なアーキテクチャ境界はコストが高い。

理由：

- 双方向のインターフェースが必要
- データ構造の分離が必要
- コンポーネント分割・ビルド・デプロイ管理が必要

そのため、最初から完全に作らず「将来のための仮置き」として部分的に作る判断がある。


スキップ・ザ・ラストステップ

完全な境界にする手前まで作って止める方法。

やること：

- インターフェースを作る
- 入出力データ構造を分ける
- 依存関係も整理する

やらないこと：

- コンポーネント分割（別デプロイ）

結果：

- 1つの塊としてビルド・実行
- でも将来分割できる構造だけ残る

メリット：

- 将来の拡張準備になる
- 運用はシンプル

リスク：

- 放置すると境界設計が崩れていく（依存が侵入する）


ワンディメンショナル・バウンダリー

より軽い境界構造。

特徴：

- インターフェース1方向のみ
- 完全な双方向分離はない

構造：

- Client → Interface → Implementation

問題点：

- 逆方向依存が起こりやすい
- チームの規律に依存する


ファサード境界

さらに単純な境界。

特徴：

- Facadeクラス1つで隠蔽
- 内部実装は外から見えない

問題：

- 内部クラスへ直接依存されやすい
- 境界が破られやすい


重要な考え方

部分境界はトレードオフ：

- コストを抑える
- ただし完全分離はしていない

つまり：

- 「将来必要になるかもしれない場所」に仮の壁を置く戦略


LAYERS AND BOUNDARIES（層と境界）

システムは単純な3層では足りないことが多い：

- UI
- ビジネスルール
- データベース

実際は複数の「関心の流れ」がある。


例：Hunt the Wumpus

構造の分解：

- GameRules（中心）
- UI（言語・表示）
- Storage（永続化）
- Network（マルチプレイ）

ポイント：

- 各関心ごとに独立した「ストリーム」がある
- GameRulesが中心で制御する


ストリーム構造

データの流れは複数方向に分かれる：

- 入力（ユーザー）
- 表示（UI）
- 保存（DB）
- 通信（ネットワーク）

それぞれが独立した経路を持つ。


境界の本質

- 境界は「関心の変化の軸」で生まれる
- すべての場所に存在しうる
- ただし作るとコストが高い


アーキテクトの判断

必要なこと：

- 境界が必要になる場所を見抜く
- まだ早いなら部分的に留める
- 必要になった瞬間に拡張できる状態にする
- 放置コストと構築コストを比較し続ける


THE MAIN COMPONENT（Mainコンポーネント）

システムには必ず1つ、「全体を起動・組み立て・制御する役割」を持つ部分がある。これが Main。


Mainの役割

Mainはシステムの中で最も低レベルなポリシー。

やっていることは主に以下：

- 依存関係の生成（Factory / Strategy など）
- DI（依存性注入）の受け取りと配布
- アプリ全体の初期化
- 実行開始（エントリーポイント）
- 外部リソースの準備

その後は制御を高レベルのロジックに渡す。


Mainの位置づけ

重要な特徴：

- OS以外からは依存されない
- システムの「入口」
- 最も具体的で汚れやすい層
- Clean Architectureでいう最外周

つまり：

Mainはアーキテクチャの“最も外側の詳細”


依存関係の役割

- DIフレームワークはMainでのみ使用
- 注入された依存はMain内部で伝播させるだけ
- 他の層はDIフレームワークを知らない


Mainの特徴（重要）

Mainには次の性質がある：

- 環境依存が集中する
- 設定・文字列・初期化処理が混ざる
- UI・ドメイン・インフラをつなぐ役割
- 変更頻度は低いが雑多になりやすい

そのため「最も汚い層」と表現される


役割分離のポイント

Mainの中にあってよいもの：

- 起動処理
- 入出力ストリーム生成
- 依存関係の組み立て
- アプリケーション開始のトリガー

Mainに置かない方がよいもの：

- ビジネスロジック
- ドメイン判断
- アプリのコア処理


例の構造的意味

提示コードの構造が示していること：

- Mainがゲーム全体を生成する
- Map生成や初期配置もMainが担当
- 入力ループもMainにある
- 実処理はすべて別コンポーネントに委譲

つまり：

Main = 起動・配線だけを担当する場所


Main = Pluginという考え方

重要な発想：

Mainはアプリの一部ではなく「プラグイン」

意味：

- Dev用Main
- Test用Main
- Production用Main
- 国・顧客ごとのMain

すべて切り替え可能


アーキテクチャ上の意味

Mainをプラグイン化すると：

- 環境差分をMainに閉じ込められる
- コアロジックは完全に独立する
- 起動構成だけ差し替え可能になる


本質

Mainはシステムの中心ではない。

むしろ：

- 最外周の配線装置
- 全体を組み立てるスクリプト層
- ビジネスルールとは切り離すべき領域


この文章の核心は「サービス（マイクロサービス）はアーキテクチャそのものではない」という主張。

サービスは単なる「プロセスやネットワーク越しの関数呼び出し」であり、それ自体が設計の本質を決めるわけではない。

本当に重要なのは次の一点。

・アーキテクチャを決めるのはサービスの分割単位ではなく「依存関係の向き」と「境界」


1. サービス分割＝アーキテクチャではない理由

サービス分割は見た目上こう見える：

- 独立している
- 別チームで開発できる
- 別々にデプロイできる

しかし実際は：

- 共有データに強く依存する
- データ形式変更で全体が影響を受ける
- 振る舞い変更が横断的に波及する

つまり「分離しているように見えるだけで結合は残っている」


2. 本当の分割線はどこか

分割すべき単位はサービスではなくこれ：

- 変化理由が同じもの同士のまとまり
- 変化理由が違うものとの境界

この境界はプロセス境界ではなく「依存の境界」


3. クロスカッティング問題

キティ配送の例が示しているのはこれ：

新機能が入ると
→ 全サービスに影響が広がる

理由は：

- 機能ごとに分けただけの構造
- 横断的なルールが分散している

つまりサービス分割は「機能分割」でしかない場合が多い


4. 本質的な解決

解決方法として提示されているのは：

- 内部にコンポーネント境界を作る
- 依存関係は内向きに統一する
- 拡張は差し替えで行う（OCP）

重要なのは：

サービス単位ではなく「サービス内部の構造」がアーキテクチャを決める


5. 結論（この章の主張）

- サービスはアーキテクチャではない
- アーキテクチャは境界と依存関係で決まる
- サービスはその入れ物にすぎない
- 重要なのはサービスの外ではなく「中身の設計」


一言でまとめると：

サービスは構造ではなく輸送手段。構造を決めるのは境界設計。


1. テストは「外部」ではなくシステムの一部

テストは単なる補助ではなく、アーキテクチャの一部として扱われる。

構造的にはこうなる：

* 本体コード：内側（ビジネスルール）
* テスト：外側（最も外周のコンポーネント）

ただし外側にあるだけで、設計対象から外れるわけではない。

2. 依存関係の向きは本体と同じ

テストも依存ルールに従う：

* テスト → 本体コードに依存
* 本体コード → テストには依存しない

つまりテストは「外側から内側を叩く構造」


3. 問題の本質：構造結合（Structural Coupling）

最も危険なのはこれ：

* テストがクラス構造に直結している状態
* 1つの変更で大量のテストが壊れる状態

例：

* クラスごとにテスト
* メソッドごとにテスト

この状態だと本体のリファクタリングが困難になる


4. 解決方法：テスト専用API

重要な考え方はこれ：

テストは「アプリの構造そのままを叩く」のではなく専用のインターフェースを通すべき

その特徴：

* UIやDBを迂回できる
* 状態を直接セットできる
* 認可や制約をバイパスできる
* テスト用に最適化された入口


5. 狙い

テスト専用APIの目的はこれ：

* テストと本体の構造を分離する
* それぞれ独立に進化できるようにする

6. 重要な副作用

分離しないと起きる問題：

* テストが壊れやすくなる
* 変更コストが跳ね上がる
* 開発者が変更を避けるようになる（＝システムが硬直）


まとめ

テストの本質は「検証コード」ではなく「外周の設計要素」。

そしてこの章の主張はシンプルで、テストは外にあるものではなく、設計された外側のレイヤーであるという一点に集約される。


1. ソフトウェアとファームウェアの境界は「変更容易性」で決まる

ここでの定義はシンプルで、

* ソフトウェア：将来の変更に耐えられる（依存が少ない）
* ファームウェア：ハード依存が強く、変更が重い

という区別。

重要なのは「ROMにあるかどうか」ではなく、
ハードウェアや環境にどれだけ引きずられているか。

⸻

2. 問題の本質は「依存の混入」

壊れる構造はこれ：

* ドメインロジック
* 通信・UI・OS・HWアクセス
* 永続化
* 割り込み・レジスタ操作

これが同じファイルや同じ層に混ざると全部が固くなる。

結果：

* 変更が全体波及
* テストは実機依存
* 移植不能

これが「全部ファームウェア化」。

⸻

3. 解決構造：レイヤと抽象化の境界

中心の考え方はこれだけ：

依存を外側（HW/OS）から内側（ビジネスロジック）へ向けない

構造としてはこうなる：

* アプリケーション（純粋なロジック）
* HAL（Hardware Abstraction Layer）
* OSAL（OS Abstraction Layer）
* ドライバ／FW
* ハードウェア

ポイントは「境界」を明確にすること。

⸻

4. HALの役割は「意味レベルを上げること」

重要な考え方：

* GPIO操作 → ハード都合
* LED ON → デバイス抽象
* LowBattery表示 → アプリ意味

上に行くほど「意味」になる。

つまりHALは単なるラッパーではなく、

ハードの詳細を「意味」に翻訳する層

⸻

5. OSも「詳細」として扱う

RTOSやLinuxも同じ扱いになる：

* OS APIを直接使う → 依存が固まる
* OSALを挟む → 交換可能になる

結果：

* OS変更が「コード修正」から「アダプタ書き換え」に変わる

⸻

6. テスト可能性が設計の正しさの指標

この章のかなり強い主張：

テストできない設計は悪い設計

理由：

* 実機依存＝遅い・壊れやすい
* UI依存＝脆弱
* HW依存＝再現不可

なので：

* テスト用API（テストハーネス）を設計に組み込む
* それもアーキテクチャの一部

⸻

7. conditional compilation（#ifdef地獄）は設計不良

本質的な批判：

* #ifdefは「抽象化の失敗」
* 仕様分岐をコンパイル時に散らすと構造が崩壊する

代替：

* インターフェースで分岐する
* 実装を差し替える（リンク or DI）

⸻

8. 「ファームウェア化」を防ぐ本質

この章の結論を一言でまとめると：

どれだけハードやOSに依存しない構造を作れるかが寿命を決める

逆に言うと：

* HWを直接触るコードが広がるほど寿命が縮む
* 抽象化できているほど長生きする

⸻

まとめ（構造だけ抽出）

この章の設計思想は結局これ：

* 依存は内向き
* HW/OSは詳細
* 詳細は外側へ追い出す
* すべては差し替え可能にする
* テスト可能性は設計の一部


1. 主張の核：「データベース＝アーキテクチャではない」

ここで言っているのは次の区別：

* アーキテクチャに関わるもの
    → データの構造・意味（ドメインモデル）
* アーキテクチャに関係ないもの
    → データベースという“保存・取得の仕組み”

つまり：

SQLやRDBMSは設計の中心ではなく「交換可能なメカニズム」

⸻

2. 重要な分離：データモデル vs データベース

混同してはいけないポイント：

* データモデル
    → 何を表すか（意味・構造）
* データベース
    → どう保存するか（技術・実装）

この章の強い主張は：

テーブル設計を中心にシステムを考えると設計が歪む

⸻

3. なぜデータベース中心設計が生まれたか

理由は技術的ではなく歴史的：

* ディスクが遅い
* だからインデックス・クエリ最適化が必要
* その結果RDBMSが発達

しかし現在のポイントは：

* それは「ハードウェア制約の副産物」
* つまりアーキテクチャ本質ではない

⸻

4. 本質的な主張：保存形式は変えてよい

システム内部の視点：

* DBは「永続化のための入れ物」
* 実際の処理では
    * list
    * tree
    * map
    * graph

などの構造に変換して使う

つまり：

DBの形のまま使うこと自体が設計ミスになり得る

⸻

5. アーキテクチャ的な正しい位置づけ

この章の整理はこうなる：

* 内側（重要）
    * ドメインモデル
    * ビジネスルール
    * データ構造の意味
* 外側（詳細）
    * RDBMS
    * ORM
    * SQL
    * ファイルシステム

⸻

6. よくあるアンチパターン

この章が強く批判しているもの：

* DBテーブル＝ドメインモデル
* ORMエンティティ＝ビジネスモデル
* SQL構造にロジックが引きずられる

結果：

* ビジネスがDBに従う構造になる
* 変更がすべて高コスト化

⸻

7. 正しい設計の方向

理想は逆：

* ドメインが中心
* 永続化は外側の適応層

構造としては：

* ドメイン（内側）
* リポジトリ（境界）
* DB（外側の詳細）

DBは「差し替え可能なストレージ」に落とす

⸻

8. パフォーマンスはアーキテクチャ外ではないが“分離可能”

主張のポイント：

* パフォーマンスは重要
* しかし設計の中心ではない
* 最適化は外側でやるべき

つまり：

性能問題でアーキテクチャを歪めるな

⸻

9. この章の本質（1行）

最も重要なメッセージはこれ：

「データの意味」は中心、「保存方法」は交換可能な詳細

⸻

10. 全体の構造（まとめ）

この章の論理構造を圧縮すると：

* データは重要
* しかしDBは重要ではない
* DB中心設計は歴史的制約の遺物
* ドメインと永続化を分離せよ
* SQLやテーブルに設計を引っ張られるな


要点は単純である。

GUIは詳細である。
ウェブはGUIである。
したがってウェブは詳細である。

アーキテクトは、そのような詳細をビジネスロジックから隔離された境界の向こう側に押し込むべきである。

ウェブはI/Oデバイスにすぎない。1960年代から我々はデバイス非依存の設計の価値を学んできた。その必要性は今も変わっていない。

もちろん、ウェブのようなGUIは非常に複雑で特殊であるため、完全な抽象化は現実的ではないという反論もある。確かにUIとアプリケーションのやり取りは密接であり、抽象化しきれない部分もある。

しかし、UIとのやり取りの中で入力が確定し、ユースケースが実行され、結果が返るという構造に切り出すことは可能である。そうすることでユースケース単位でUIから独立させることができる。

このような抽象化は容易ではなく、何度も試行錯誤が必要になる。しかし実現は可能である。そしてマーケティングが常に変化を要求する以上、この分離はしばしば不可欠となる。



非対称な結婚

あなたとフレームワーク作者の関係は極端に非対称である。

あなたはフレームワークに大きな投資と依存をする必要があるが、フレームワーク作者はあなたに対して何の責任も負わない。

ここは重要な点である。

フレームワークを使うとき、あなたはドキュメントを読み、それに従って自分のシステムをフレームワークに合わせるように設計することが求められる。多くの場合、それはアーキテクチャをフレームワークに合わせて包み込むことを意味する。

ベースクラスを継承し、ビジネスオブジェクトにフレームワークの仕組みを組み込むよう促される。つまりアプリケーションをフレームワークに密結合させる方向に誘導される。

フレームワーク作者にとっては、それはリスクではない。自分のコードだからだ。むしろユーザーが強く依存してくれるほど望ましい。

結果としてユーザーはフレームワークに“結婚”させられる。大きな長期契約を一方的に背負うことになる。

一方でフレームワーク作者はユーザーに対して何の長期的責任も負わない。この構造は完全に片側的である。

⸻

リスク

主なリスクは次のようなものになる。

フレームワークはアーキテクチャ的にクリーンでないことが多い。依存関係のルールを破り、内側のビジネスオブジェクトにフレームワークを継承させようとすることがある。結果として内側の領域がフレームワークに侵食される。

初期段階では便利でも、プロダクトが成長するとフレームワークの制約が足かせになることがある。

フレームワークが進化して方向性が変わると、追従コストが発生する。過去の機能が消えたり変更されたりすることもある。

より良い代替フレームワークが出ても簡単には移行できない。

⸻

解決策

結論は単純である。

フレームワークと結婚してはいけない。

使うこと自体は問題ではない。ただし依存しすぎないことが重要である。フレームワークはアーキテクチャの外側に置くべきであり、内側に入り込ませてはいけない。

もしフレームワークがベースクラス継承を要求するなら、それを直接ビジネスオブジェクトに適用してはいけない。代わりにプロキシやアダプタを作り、それを外側のコンポーネントとして扱う。

ビジネスルールはフレームワークを知らない状態に保つべきである。

例えばSpringのようなDIフレームワークを使う場合でも、@Autowiredをビジネスロジックの中に散らしてはいけない。フレームワークを知っていてよいのは最も外側の構成要素だけである。


結婚せざるを得ないもの

すべてのフレームワークを避けられるわけではない。標準ライブラリなどは事実上避けられない場合もある。

ただしそれも「選択として結婚した」という認識が重要である。選択の自覚があるかどうかで設計の質が変わる。


結論

フレームワークを使うときは、すぐに結びつかないことが重要である。しばらく距離を保ち、そのままでも設計が成立するかを確認するべきである。

可能であれば、フレームワークをアーキテクチャの境界の外に置いたまま利用する方法を探すべきである。

牛を買わずに牛乳だけ得る方法を探すべきである。

⸻

ユースケース分析

図33.1は典型的なユースケース分析を示している。

4つの主要なアクターが存在する。
単一責任の原則に従えば、これら4つのアクターはシステムにおける主要な変更理由になる。

機能追加や変更は必ずいずれかのアクターのために行われる。
したがって、あるアクターの変更が他のアクターに影響しないように分離すべきである。

図に含まれるユースケースは完全な一覧ではない。
例えばログイン・ログアウトは省略されている。
これは説明を簡潔にするためである。

中央にある点線のユースケースは「抽象ユースケース」である。
これは他のユースケースに共通の方針を定義し、それを具体化する役割を持つ。

例として「View Catalog」は以下に分かれる：

* ViewerとしてのView Catalog
* PurchaserとしてのView Catalog

これらは抽象ユースケースを継承している。

この抽象化は必須ではないが、早い段階で共通性を認識することには価値がある。

コンポーネントアーキテクチャ

次に、アクターとユースケースをもとに初期のコンポーネント構造を設計する（図33.2）。

図の二重線はアーキテクチャ境界を示す。
典型的な分割として以下がある：

* views
* presenters
* interactors
* controllers

これらはさらにアクターごとに分割されている。

各コンポーネントは .jar や .dll として分離可能な単位になる。

特別な例として「Catalog View」「Catalog Presenter」がある。
これは抽象ユースケースを扱うための構造であり、共通クラスとして定義され、各アクター側の実装がそれを継承する。

⸻

実際の分割について

本当にこの粒度でjarに分けるかどうかは状況次第である。

* ビルド単位としては完全分離する
* デプロイ単位は統合する場合もある

例えば以下のような構成が考えられる：

* views / presenters / interactors / controllers / utilities の5分割
* views+presenters と、それ以外の2分割
* すべてを1つにまとめる単純構成

重要なのは「後から変更できる状態を保つこと」である。

⸻

依存関係の管理

図33.2の制御フローは右から左へ流れる。

* 入力は controller
* 処理は interactor
* 整形は presenter
* 表示は view

ただし依存関係の矢印は必ずしも同方向ではない。
多くは逆方向を向いている。これは依存性のルールに従っているためである。

依存は常に高レベルポリシー側へ向かうように設計される。

* using関係：制御の流れと同じ方向
* inheritance関係：制御の流れと逆方向

これはOpen–Closed原則により、低レベルの変更が上位に波及しないようにするためである。

⸻

結論

このアーキテクチャは2つの分離軸を持つ：

1. 単一責任の原則に基づくアクター分離
2. 依存性ルールに基づくレイヤ分離

目的は「変更理由が異なるもの」と「変更速度が異なるもの」を分離することである。

この構造により、システムは柔軟にデプロイ形態を変えられる。
必要に応じてコンポーネントを再構成し、状況に適した形で再配布できる。


この章の核心は、「どれだけ優れたアーキテクチャ理論を持っていても、実装のやり方次第で簡単に壊れる」という点にある。

まずコードの構成方法として、レイヤー分割（web・service・repository）、機能単位の分割、ポートとアダプタ、コンポーネント単位など複数の設計スタイルが紹介される。
これらは一見すると異なるアーキテクチャに見えるが、実装が雑になると本質的な違いは消えてしまう。

特に問題になるのが「すべてをpublicにする」ような設計である。
これをやるとパッケージの境界が意味を失い、どの設計スタイルでも実質的に同じ構造になってしまう。つ
まりアーキテクチャ上のルールは存在しているように見えても、実際には守られていない状態になる。

本来パッケージやモジュールは「依存関係を制御し、アクセスを制限するための仕組み」である。
しかし可視性を適切に使わないと、それは単なるフォルダ分けに過ぎなくなる。

一方で、言語のアクセス制御（Javaのpackage-privateなど）を正しく使えば、コンパイラレベルでアーキテクチャを強制できる。
これは設計ルールを「気合やレビュー」に頼るのではなく、「壊せない構造」として実装できるという意味になる。

さらに、ソースコードの分割方法（ドメインとインフラを分ける、コンポーネント単位で分けるなど）
によっても依存関係の形は変わるが、これも適切に管理しないと内部から簡単に破綻する。

結論として、この章が伝えているのは次の一点に集約される：

アーキテクチャの違いは設計図ではなく実装で決まる。
そして最も重要なのは、言語機能や構造を使って依存関係を強制すること。
