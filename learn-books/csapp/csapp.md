すべてのコンピュータには**ワードサイズ（word size）**がある。
ワードサイズとは、そのコンピュータが扱うポインタの標準的なサイズを表す。
仮想アドレスはこのワードサイズで表現されるため、ワードサイズによって決まる最も重要な要素は、
  仮想アドレス空間の最大サイズ
ワードサイズが w ビットのコンピュータでは、仮想アドレスは
  0 ～ 2^w - 1
の範囲を表現できる。

したがって、プログラムがアクセスできる最大メモリ空間は
  2^w バイト
になる。

2^32 = 約43億
2^64 = 16エクサバイト(約1.84 × 10^19バイト)

多くの64ビットマシンは、32ビット向けにコンパイルされたプログラムも実行できる。
これを後方互換性（backward compatibility）と呼ぶ。


$ gcc -m32 prog.c

でコンパイルしたプログラムは、
* 32ビットマシン
* 64ビットマシン
の両方で実行できる。

$ gcc -m64 prog.c

でコンパイルしたプログラムは、64ビットマシンでしか動きません。

そのため、「32ビットプログラム」「64ビットプログラム」
という表現は、実行するコンピュータではなく、どの設定でコンパイルされたかを指す。


char型について

char型は1バイトです。
元々は文字を保存するための型ですが、整数としても利用できます。

注意点として、charが
* signed char
* unsigned char

int, long型のサイズは環境によって異なっていたのでint32_t、int64_tなどの固定サイズ型が導入された。

ポインタのサイズはワードサイズに依存。

プログラマは、異なる環境でも動作するプログラムを書くべき。

次は第3章からはじめる

linux> gcc -Og -o p p1.c p2.c

このコマンドの gcc はCコンパイラを指す。
Linuxではこれが標準コンパイラなので、単に cc として呼び出すこともできる。

コマンドラインオプション -Og は、コンパイラに対して最適化を行うよう指示するが、その際に元のCコードの構造をある程度保つレベルの機械語を生成するように指定している。

より強い最適化を行うと、生成されるコードは大きく変形され、元のソースコードとの対応関係が理解しにくくなる。そのため本書では学習目的として -Og を用いる。
その後、最適化レベルを上げたときに何が起こるかも確認していく。

実際には、より高い最適化（例えば -O1 や -O2）を使ったほうが、実行性能の観点ではより望ましい。
gccコマンドは、ソースコードを実行可能コードへ変換するために、一連のプログラムを順に呼び出す。

まず、Cプリプロセッサがソースコードを展開する。ここでは #include によって指定されたファイルを取り込み、#define によるマクロを展開する。

次にコンパイラは、2つのソースファイルそれぞれに対してアセンブリコードを生成する。この結果として p1.s と p2.s というファイルが得られる。

続いてアセンブラがアセンブリコードをバイナリ形式のオブジェクトファイルに変換する。この結果 p1.o と p2.o が生成される。

オブジェクトコードは機械語の一種であり、すべての命令はバイナリ表現されている。ただし、この時点ではグローバル変数などのアドレスはまだ確定していない。

最後にリンカが、これらのオブジェクトファイルと、printf などのライブラリ関数のコードをまとめて、最終的な実行可能ファイル p を生成する（-o p で指定した名前）。

実行可能コードは機械語のもう一つの形であり、実際にプロセッサが実行する完全なコード。

これら異なる機械語の形態とリンキング処理の関係については、第7章でより詳しく説明される。


第一に、機械レベルプログラムの形式と動作は命令セットアーキテクチャ（ISA: Instruction Set Architecture）によって定義される。ISAはプロセッサの状態、命令の形式、そして各命令が状態に与える効果を規定する。

x86-64を含む多くのISAでは、プログラムの動作は「命令が順番に実行される」と仮定して記述される。つまり、ある命令が完了してから次の命令が開始されるというモデルである。

実際のプロセッサ内部ははるかに複雑で、多数の命令を並行して実行しているが、その結果がISAで定義された逐次実行と一致するように制御されている。

第二に、機械レベルプログラムが使用するメモリアドレスは仮想アドレスである。仮想アドレスは、あたかも非常に大きなバイト配列が存在するかのようなメモリモデルを提供する。

実際のメモリは、複数のハードウェアとオペレーティングシステムソフトウェアの組み合わせによって実現されており、その詳細は第9章で説明される。


プログラムカウンタ（PC）

Cでは異なるデータ型のオブジェクトがメモリ上に定義・配置されるが、機械語ではメモリは単なるバイト単位でアクセス可能な大きな配列として扱われる。

配列や構造体などの複合データ型は、連続したバイト列として表現される。

さらにアセンブリレベルでは、符号付き・符号なし整数の区別や、ポインタ型と整数型の区別すら明示的には存在しない。

プログラムメモリには、実行可能な機械語、オペレーティングシステムが必要とする情報、関数呼び出しを管理するためのスタック、そしてmallocなどによって動的に割り当てられるメモリ領域が含まれる。

前述の通り、プログラムメモリは仮想アドレスで管理される。x86-64では64ビットのアドレス空間が使われるが、現実の実装では上位16ビットは0でなければならない。そのため実際に使用可能なアドレス空間は最大で2^48（約64TB）となる。

通常のプログラムが利用する範囲は数MBから数GB程度である。オペレーティングシステムはこの仮想アドレス空間を管理し、仮想アドレスを物理メモリの実アドレスへと変換する。

じゃあ物理アドレスは誰が見ているかというと、中心はMMU（Memory Management Unit）。ただし「MMUが管理している」というよりは、

・CPUのMMUが変換を実行する
・その変換ルール（ページテーブル）をOSが作る

という分業構造になってる。

⸻

OSの立ち位置が少しポイントで、

OSも通常の意味では「物理アドレスを直接全部把握して操作している存在」ではない。

実際はこういう関係：

・OSは物理メモリ上の空き領域を管理している（ページフレーム管理）
・その上で「この仮想アドレスはこの物理ページね」という対応表（ページテーブル）を作る
・そのページテーブルをCPUに渡す

つまりOSは“物理メモリを管理するが、アクセスは常に仮想経由”という立場。

ただし例外的にOSカーネル内部では：

・特権モード（kernel mode）で動くコードは
・必要に応じて物理メモリを扱うロジックを書くことはある
・でもそれも「アドレス変換機構の外側で裸のポインタを触る」という意味ではない

最近のOS（Linux含む）は基本的に「物理アドレスを直接いじる設計」はかなり限定的。
